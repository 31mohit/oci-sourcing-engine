# PRD: Mini Sourcing Engine on OCI

Oct 20, 2026 · @Mohit

## 1. Overview

This project builds a deliberately thin candidate-matching app and runs it like a production system on Oracle Cloud Infrastructure (OCI), to show Cloud Operations Engineer skills for the Kodiva.ai role (OCI production, hybrid in Pune).

The app ranks synthetic resumes against a job description and learns from recruiter accept/reject feedback. The real deliverable is the operations layer around it: infrastructure as code, CI/CD, monitoring and alerting, reliability, security, cost control and a documented incident.

**Goals**

- Provision and operate a complete stack on OCI using Terraform, at no cost on the Always Free tier where possible.
- Show monitoring, alerting, backup and incident response with evidence (dashboards, alarms, runbook, postmortem).
- Cover the common requirements of Cloud Operations Engineer job descriptions: monitoring, IaC, CI/CD, Linux, scripting, security, incident management.
- Finish with a portfolio package a hiring manager can review in 10 minutes.

## 2. Scope and constraints

The project covers one small app and the full operations layer around it; anything that does not strengthen the operations story is out of scope.

| In scope | Out of scope |
| --- | --- |
| Resume parsing, embedding and ranking (simple, placeholder first) | Claims of ranking accuracy or fairness |
| Recruiter accept/reject feedback that re-weights ranking | Real candidate data or any PII |
| Outreach email drafts for human approval (templates first) | Sending real emails, LinkedIn or WhatsApp automation |
| Terraform on OCI, Docker, CI/CD, monitoring, alerting | A production-grade UI or multi-user auth |
| Backup, Vault, audit logs, budget alerts | Kubernetes (OKE) unless free credit allows a one-off demo |
| One simulated outage with runbook and postmortem | Out-competing Kodiva's own product |

**Constraints**

- Cost target: US$0. Use OCI Always Free resources and free tools; set a budget alert on day one.
- Data: synthetic resumes only, generated by a script.
- Time: a focused system that works reliably beats an ambitious one that does not.

## 3. Users and use cases

There are two users: a recruiter who uses the app, and you as the operator who keeps it running.

| User | Use case |
| --- | --- |
| Recruiter | Submit a job description and a pool of synthetic resumes, and get a ranked shortlist |
| Recruiter | Accept or reject candidates so later rankings improve |
| Recruiter | Review and approve outreach drafts before anything is sent |
| Operator | See system health on a dashboard and get alerted before users notice a problem |
| Operator | Deploy a change safely, roll it back, and recover from a failure using a runbook |

## 4. Functional requirements (the thin app)

The app needs only enough behavior to give the operations layer something real to run, monitor and break.

| ID | Requirement | Priority |
| --- | --- | --- |
| FR-1 | Generate synthetic resumes with a script (no real PII) | Must |
| FR-2 | `/health` endpoint reporting API, queue and database status | Must |
| FR-3 | Submit a job description and resume pool; enqueue a ranking job | Must |
| FR-4 | Worker parses resumes (plain Python), embeds them with a small open-source model and ranks by cosine similarity | Must |
| FR-5 | Return a shortlist with a score per candidate | Must |
| FR-6 | Record accept/reject decisions as events with an idempotency key | Must |
| FR-7 | Re-weight future rankings from feedback using a versioned weighted score | Should |
| FR-8 | Draft outreach emails from templates for human approval; schedule follow-ups through the queue | Should |
| FR-9 | Expose Prometheus metrics: queue depth, job duration, failures, weights version | Must |

## 5. Architecture

&#91;embedded content: architecture · app tier, data tier, ops layer\]

One small VM runs the app, queue, Prometheus and Grafana as containers. Terraform builds everything, GitHub Actions deploys it, and OCI Vault, the database, Object Storage and OCI Monitoring are managed services. Docker Compose replaces Kubernetes to stay inside the free tier.

## 7. Non-functional requirements and SLOs

These targets are demo values you choose and defend; the alerts in OR-5 are written against them.

| Target | Value (starting point) | How it is measured |
| --- | --- | --- |
| Availability of the API | 99% over 30 days | Blackbox probe on `/health` |
| Ranking request latency | p95 under 2 seconds for 100 resumes | Prometheus histogram |
| Failed jobs | Under 2% of jobs over 1 hour | Job failure counter |
| Queue depth | Under 50 waiting jobs for more than 5 minutes | Queue length gauge |
| Recovery time (RTO) | Under 30 minutes from the runbook | Timed during the outage drill |
| Recovery point (RPO) | Under 24 hours | Backup schedule |
| Cost | US$0 per month | Budget alert and cost report |

## 8. Phased delivery plan

Build the operations layer first and the app last. Each phase has a done criterion, so you always have something working to show.

1. **Setup:** Create the OCI account, set a budget alert, create the GitHub repository and install Terraform, Docker and the OCI CLI. Done when `oci iam region list` works and the budget alert exists.
2. **Stub app:** Write a FastAPI service with `/health`, a job endpoint, a Redis queue and a worker with a placeholder ranker; generate synthetic resumes; containerize it. Done when `docker compose up` runs the full flow locally.
3. **Infrastructure:** Write Terraform for the VCN, subnets, NSGs, A1 VM, database, Object Storage and Vault. Done when `terraform apply` builds everything and `terraform destroy` removes it.
4. **Deployment:** Add the GitHub Actions pipeline and deploy to the VM, with rollback. Done when a push to main updates the running app.
5. **Monitoring and alerting:** Add metrics, Prometheus, the Grafana dashboard, OCI alarms and Notifications. Done when a test alert reaches you.
6. **Reliability and security:** Add retries and idempotent jobs, move secrets to Vault, enable audit logs, and set up backups with a tested restore. Done when you can restore from backup.
7. **Incident drill:** Break the system on purpose (for example kill the worker and fill the queue), recover it with the runbook, and write the postmortem. Done when the postmortem is published.
8. **App improvements (optional):** Replace the placeholder ranker with real embeddings, add the feedback loop and template-based outreach drafts.
9. **Portfolio package:** Write the README, architecture diagram and screenshots, then apply with the repository link.

## 10. Risks, limitations and ethics

| Risk or limitation | Mitigation |
| --- | --- |
| A1 instances are often out of capacity in a region | Retry script, try different times of day, split services across smaller VMs |
| Spending beyond the free tier | Budget alert on day one; check the Limits, Quotas and Usage page; destroy unused resources |
| Cross-region backup may cost money | Back up to a second bucket first; describe the cross-region design in the runbook |
| Scope creep into the AI part | Placeholder ranker first; improve only after the ops layer works |
| Ranking models can encode bias | Label the app a demo, make no accuracy claims, keep a human approving every decision |
| Candidate data is sensitive personal data | Synthetic resumes only; no real PII anywhere in the repository or cloud |
| Platform terms and consent problems | No LinkedIn or WhatsApp automation; no real emails sent |
| Feedback loops can amplify a recruiter's biases | Version the weights, log every decision and allow rollback |

## 11. Success criteria and interview talking points

The project is done when each item below is true and you can show it.

- [ ] `terraform apply` builds the whole stack from scratch and `terraform destroy` removes it
- [ ] A push to main deploys the new version automatically, and a rollback works
- [ ] The Grafana dashboard shows queue depth, failed jobs and latency
- [ ] A deliberately triggered alarm sends a notification
- [ ] Secrets come from Vault, with none in the repository
- [ ] A backup was restored successfully and the time was recorded
- [ ] The simulated outage was recovered within the RTO target, with a runbook and postmortem written
- [ ] Monthly cost stays at US$0

**What to say in an interview**

- You treated the app as a thin workload and spent your effort on running it reliably.
- You can walk through one real incident: detection, diagnosis, recovery and what you changed afterwards.
- You chose free-tier resources deliberately and can explain the trade-offs (for example Docker Compose over Kubernetes).
- You handled the ethics honestly: synthetic data, no accuracy claims, a human approving decisions.
